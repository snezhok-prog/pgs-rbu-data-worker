# Контракт внешнего обработчика РБУ, версия 1

Один worker выполняет операции по направлениям `ADVERTISING`, `TRADE` и `PET`. Неизвестное направление или операция отклоняются. Для повторяемых испытаний используется отдельный topic на каждый запуск; общий production topic и идентификацию сервиса согласовывает команда развёртывания.

## Переменные external task

| Переменная | Значение |
| --- | --- |
| `mainId` | ID собственного дела в ПГС |
| `collectionName` | `rbuModulesAppeals.subservices` для текущего испытательного контура |
| `camundaBusinessInfoId` | Идентификатор бизнес-процесса, совпадающий с `subservices[*].camundaProcessInfo.camundaBusinessInfoId` |
| `rbuDomain` | `ADVERTISING`, `TRADE` или `PET` |
| `rbuProfile` | `ROIV` или `OMSU` |
| `rbuOperation` | Одна из операций таблицы ниже |
| `rbuContractVersion` | Строка `1` |

Подуслуга должна однозначно соответствовать текущему `processInstanceId` и бизнес-процессу. И standalone Main, и Spring-адаптер требуют непустой `worker.standardCodes` и проверяют точный номер этой подуслуги до выполнения операций. Передаваемые ID не подтверждают полномочия сами по себе: worker перечитывает дело, паспорт субъекта/МО, карточку и кабинет организации. XLSX загружается в хранилище ПГС; в деле хранится `importFile` с его метаданными. Содержимое файла и массив строк в Camunda не передаются.

Для торговли в деле также выбирается `dataType`: `НТО`, `Рынки` или `Ярмарки`. Приоритеты чтения полей сохранены в адаптере `TradeDomain`; серверные записи контекста перечитываются независимо от присланных названий.

Для питомца используются `dataType=Мой питомец` и служебные коллекции `rbuPetRegionPassports`, `rbuPetRegionMunicipalities`, `rbuPetRegionOrganizations`. Проверяются действующий доступ `serviceCode=673151`/`serviceDomain=MY_PET`, связи региона/МО/организации, текущий GUID кабинета и право самостоятельного импорта ОМСУ. На каждом рабочем листе название и ОГРН сверяются с выбранной организацией; «Хвост» обязателен. Нормализуется пробельный край заголовка «Наименование приюта», но значения ячеек не переписываются произвольно.

## Операции

| Операция | Предусловие и результат |
| --- | --- |
| `PARSE_VALIDATE` | Читает XLSX и разрешённые метаданные приложений; проверяет структуру, значения, контекст, дубли и лимиты. Сохраняет компактный результат в деле, полные строки — в устойчивом журнале worker. Ошибочный файл возвращает результат валидации; целевые записи не создаются. |
| `IMPORT_APPLY` | Требует актуальную успешную валидацию и подтверждение. Записывает не более 50 физических записей за вызов. Возвращает `rbuApplyHasMoreBatches=true`, пока остались порции. Повтор использует сохранённые идентичности и проверяет прежнее содержимое. |
| `IMPORT_FINALIZE` | Проверяет доверенный завершённый журнал импорта; подтверждает результат `APPLIED`. Не заменяет штатное завершение дела ПГС. |
| `IMPORT_CANCEL` | Отменяет импорт до начала применения. Для уже начатого/применённого импорта нужна отдельная процедура отката. |
| `ROLLBACK_PREPARE` | Требует штатно завершённое исходное дело и доверенный журнал нового worker. Формирует план удаления и перечень блокирующих причин. |
| `ROLLBACK_EXECUTE` | Проверяет подтверждение текущего плана, владельца, ID/GUID, исходное содержимое и активные ссылки перед удалением. Удаление, ответ которого потерян, проверяется чтением; слепого повтора нет. |
| `ROLLBACK_FINALIZE` | Подтверждает выполнение подготовленного плана. Не подменяет финальный статус дела ПГС. |

Результаты операции сохраняются в корневом деле и соответствующей подуслуге (`rbuImportDraft`, `rbuImportResult`). Для торговли журнал созданных записей находится в `subservices[*].migrationCreatedRecords`, сводка — в `tradeMigrationSummary`. В переменные процесса возвращаются только скаляры: статус, возможность применения, количества и признак следующей порции.

## Подтверждение торговли и питомца

После `PARSE_VALIDATE` клиент перечитывает дело и копирует **актуальный** `importDraft.confirmationFingerprint` в:

```json
{
  "rbuImportConfirmation": {
    "confirmApply": true,
    "confirmationFingerprint": "текущий отпечаток из результата проверки"
  }
}
```

Этот объект записывается в `xsdData` текущей подуслуги, затем завершается пользовательская задача подтверждения. Одного `confirmApply=true` недостаточно. Worker проверяет неизменность файла, типа данных, версий, отпечатка и доверенного `workerValidationKey`; изменение одного из входов требует новой проверки. Старая экранная форма с `validationFingerprint` несовместима с этим контрактом без адаптации.

## Сбои и эксплуатационные границы

Перед CREATE/DELETE сохраняется намерение операции. При неоднозначном результате следующая попытка сначала ищет подтверждение; автоматически повторять CREATE при отсутствии однозначного результата запрещено. Режим `local-single` требует одного экземпляра и сохранённой папки журнала. Перезапуск с пустой папкой не является восстановлением.

Техническая ошибка не превращается в успешный результат. В лог выводятся ID задачи/процесса, направление, профиль, операция, длительность и безопасное описание. HTTP-ошибка содержит метод и путь без query и тела. После достижения локального предела попыток требуется разбор оператора; это не гарантирует incident Camunda ровно после третьей ошибки.

Откат торговли поддерживает только новые импорты `pgs-trade-external-v1` с доверенным `APPLIED`-журналом. Исторические импорты Groovy, перенос старых журналов и уже запущенные процессы требуют отдельной процедуры. Для промышленной работы нескольких worker необходимы общий устойчивый журнал, согласованные блокировки и подтверждённый контракт идентификации, файлов и повторов.

Испытательная BPMN не является готовой заменой опубликованного стандарта ПГС. Полный состав обязательной адаптации форм и listeners перечислен в [объёме торговли](trade-scope.md).

## Журнал питомца и удаление данных

PET пишет шесть реестров: `animalCatchOrderRegistryCollection`, `animalsRecordsCollectionTwo`, `animalCatchActRegistryCollection`, `myPetAnimalCardReestr`, `animalReleaseActRegistryEntry`, `animalTransferActRegistryCollection`. Связанные изменения существующих записей сохраняются отдельными PATCH-намерениями и учитываются в том же лимите 50 физических изменений. Возврат прежнего состояния допускается только при совпадении текущего содержимого с последним записанным worker.

Доверенная сводка PET — `petMigrationSummary`, публичные журналы — `migrationCreatedRecords` и `migrationPatchedRecords`. План удаления — `rbuPetRollbackPlan`, результат — `rbuPetRollbackReport`. Для `ROLLBACK_EXECUTE` требуется `xsdData.rbuPetRollbackConfirmation` с `confirmFinalRollback=true`, актуальными `targetAppealId` и `journalFingerprint`. Поля подтверждения не заменяют сверку с сохранённым серверным планом.

Состояния строки: `PENDING`, `DELETED`, `ALREADY_DELETED`, `BLOCKED`, `ERROR`; для каждого сохраняется причина. `initialBlockedRecords` показывает блокировки при подготовке, `pendingRecords` — ещё ожидающие строки, `notDeletedRecords` — все остающиеся строки, включая ожидающие, блокировки и ошибки. Отсутствовавшая запись учитывается в `alreadyDeletedRecords`, а не как техническая ошибка. Контрольная точка хранится в UTC, отображение `checkpointTimeDisplay` явно содержит московскую зону. Продолжение определяется серверным журналом, не browser tab lock.

[Точечные шаблоны PET для ПГС](../integration/pet/README.md) сохраняют исходные идентификаторы и штатные операции номера/статусов/уведомлений. Они требуют отдельной публикации и проверки в интерфейсе; прямой DEV-прогон этого не подтверждает. Старые Groovy-импорты без доверенного журнала нового worker автоматически к откату не допускаются.
