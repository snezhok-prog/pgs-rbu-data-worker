# Торговля: объём переноса и исходные правила

Пакет переносит массовый разбор XLSX, валидацию, применение импорта и контролируемый откат в общий Java external-task worker. Три профиля данных: **НТО, рынки, ярмарки**. Экранные формы и работа с одной записью остаются отдельным объёмом.

## Источники

## Контракт операций

Поддерживаются `PARSE_VALIDATE`, `IMPORT_CANCEL`, `IMPORT_APPLY`, `IMPORT_FINALIZE`, `ROLLBACK_PREPARE`, `ROLLBACK_EXECUTE`, `ROLLBACK_FINALIZE`. Прикладной контракт — `pgs-trade-external-v1`, версия парсера — `rbu-trade-4.0`, валидации — `rbu-trade-validation-4.3`. Номер версии внутри JSON-конфигурации не заменяет версию рабочего контракта.

РОИВ выбирает целевую организацию в своём разрешённом регионе. Кабинет координатора и владелец импортируемых записей могут различаться. Worker перечитывает организацию координатора и её регионы, паспорт, МО, карточку торговли и целевой кабинет; проверяет область полномочий, связи, `registryScope=TRADE` и актуальный GUID организации. Контексту из присланного XLSX или изменяемого черновика без этих проверок доверять нельзя.

ОМСУ работает только со своей организацией. Для применения импорта требуется `isMigration=true`; самостоятельная валидация своей организации допускается без этого разрешения. Данные о владельце целевой записи формируются из проверенного серверного контекста.

Импорт разрешён только после проверки без ошибок: частичный импорт корректных строк при наличии ошибочных строк не допускается. Перед записью проверяются ID и SHA-256 файла, тип данных, версии, доверенный снимок валидации и актуальное подтверждение пользователя. Изменение файла или подтверждения требует новой проверки.

Файлы и фотографии разрешаются из метаданных документов дела в группах «Файлы для загрузки в реестр» или «Файлы миграции». Произвольные сетевые адреса и пути из ячеек не скачиваются. Группа с тем же назначением может распознаваться по исходному техническому идентификатору, сохранённому в коде; рабочие файловые ID в документацию не переносятся.

## Лимиты и повтор после сбоя

- XLSX: не более 20 МиБ; не более 5000 строк данных.
- Архив XLSX: не более 10000 элементов, один распакованный элемент — не более 50 МиБ, суммарно — не более 100 МиБ.
- Один импорт: не более **2500 физических записей**, включая зеркальные справочники. Проверка по числу строк без учёта связанных записей недостаточна.
- Применение выполняется порциями не более 50 записей. XLSX и полные массивы строк не помещаются в переменные Camunda.
- Перед созданием сохраняется устойчивое намерение операции; после создания проверяются ID, GUID, владелец, происхождение и бизнес-хеш. Повтор после потери ответа не должен создавать ещё одну запись. Возобновление останавливается при внешнем изменении уже созданных данных.
- Рабочий режим `local-single` рассчитан на **один worker и сохранённую папку журнала**. Нельзя удалять журнал между повторами и считать новый пустой журнал эквивалентом продолжения.

Для нескольких экземпляров требуются общий устойчивый журнал, распределённая блокировка и серверные гарантии конкурентного изменения. Локальные проверки одного worker не доказывают наличие CAS/fencing на сервере и не заменяют согласованную нагрузочную приёмку.

## Откат

Физический откат допускается для штатно завершённого исходного дела и доверенного журнала успешно применённого импорта. Подготовка плана и удаление сверяют первоначальные ID/GUID, владельца, происхождение, бизнес-хеш и действующие ссылки. Изменённые или используемые записи блокируют удаление; проверка повторяется непосредственно перед удалением.

Worker v1 откатывает только собственные новые импорты с контрактом `pgs-trade-external-v1` и подтверждённой устойчивой контрольной точкой. Исторические Groovy-импорты без такого журнала не принимаются. Уже запущенные дела и перенос старых журналов требуют отдельного решения.

В текущем цикле откат проверяется **локально**. Переводить тестовое дело DEV вручную в `complete`, чтобы пройти предусловие, запрещено. Прямое завершение процесса Camunda также не считается штатным завершением дела ПГС. Живую проверку отката можно добавить только после получения исходного завершённого дела штатным путём и отдельной фиксации этого результата.

## Что этот пакет ещё не подтверждает

Испытательный [trade-acceptance.bpmn](../bpmn/trade-acceptance.bpmn) — отдельный процесс для проверки external tasks. Он не является штатной выгрузкой стандарта ПГС и не заменяет формы, права, кнопки, регистрацию, нумерацию и финальные статусы дела.

Для подключения штатных стандартов требуется отдельно адаптировать обработчики регистрации, повторной загрузки и подтверждения под компактный результат worker. Исходный обработчик подтверждения отката сам выполняет DELETE из браузера; его нельзя оставить одновременно с серверным `ROLLBACK_EXECUTE`. Текущий Java-контракт также не переносит автоматическую массовую настройку подписок пользователей из listeners уведомлений РОИВ. Эти части нельзя молча удалить или объявить проверенными при замене только script tasks.

Живые испытания DEV ведутся отдельным протоколом. Наличие исходников, успешные локальные тесты или эта карта не означают, что все DEV-сценарии уже пройдены. Проверка нативного UI и финального статуса ПГС, DEV-откат и работа с одной записью остаются отдельными этапами. Питомец также реализуется и принимается отдельно от торговли и рекламы.
