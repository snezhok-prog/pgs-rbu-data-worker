# PET: пакет изменений штатных BPMN и форм ПГС

Пакет подготовлен по текущим source-настройкам и опубликованным схемам PSI от 29.10.2026. Тяжёлые Groovy-операции и браузерная обработка XLSX/массовое удаление заменены вызовами Java worker. Исходные идентификаторы процессов, задач, событий, вкладок и штатные операции номера, статуса и уведомлений сохранены.

Это локальные интеграционные шаблоны. Они не загружались в PSI или DEV, не публиковались в ПГС и не подтверждают штатную регистрацию, работу экранных форм либо финальный статус дела. Приёмочные BPMN из `tools/dev-cli/templates` остаются отдельными процессами.

## Контракт external task

Шаблоны используют выбранный topic `pgs-rbu-data-processing-v1`. У работающего сервиса `worker.topic` должен иметь точно такое значение. Это выбранное значение интеграции: корпоративный poller читает настройку из внешнего файла, а его fallback `pgs-data-processing-v1` не является доказательством штатного topic на целевом стенде.

Каждая заменённая задача передаёт локальные input-параметры `rbuDomain=PET`, `rbuProfile=ROIV|OMSU`, `rbuContractVersion=1`, `collectionName=rbuModulesAppeals.subservices` и `rbuOperation`. `mainId` и `camundaBusinessInfoId` читаются из уже созданных штатным процессом переменных. Подставлять произвольные идентификаторы вместо контекста регистрации нельзя.

Операции: `PARSE_VALIDATE`, `IMPORT_APPLY`, `IMPORT_FINALIZE`, `IMPORT_CANCEL`, `ROLLBACK_PREPARE`, `ROLLBACK_EXECUTE`, `ROLLBACK_FINALIZE`. Цикл исходного импорта использует выход worker `rbuApplyHasMoreBatches`. Для отката добавлен шлюз `Gateway_PetExternalRollbackBatch` и два перехода по `rbuRollbackHasMore`; старый переход `Flow_0v18ir6` сохранён как выход к финализации. Одна доставка worker выполняет не более 50 физических изменений.

В `47615` операция записи выполняется ровно в `Activity_PetProcessOneRow`. Прежняя подготовка `Activity_RbuApplyImport` и завершение `Activity_PetFinishBatch` содержат короткие проверки разрешения импорта и согласованности `rbuApplicationStatus`/`rbuApplyHasMoreBatches`. Они не читают файлы, не создают записи и не считают строки. Цикл с теми же ID возвращается через эти проверки; `IMPORT_FINALIZE` вызывается прежней задачей `Activity_RbuPersistPetJournal` после последнего пакета. Source/runtime diff заменяют оба браузерных XLSX-парсера этой копии; две формы показывают серверные счётчики созданных записей и обновлённых связей.

## Изменения настроек ПГС

[manifest.json](manifest.json) содержит исходные и новые SHA-256, точные task IDs, операции, изменения переходов, идентификаторы стандартов/runtime и ссылки на JSON diff.

- `patches/*-standard.json` задают изменения исходного стандарта: регистрационные обработчики в `appealData.statuses[*].actions[*].handler`, обработчики событий в `process.catchEvents[*].handler` и инициализаторы `additionalDataTabs[*].xsdHandlers`.
- `patches/*-runtime.json` задают соответствующую опубликованную форму данных: `statusModel`, `camundaProcess.catchEvents[*].handlers` и `xsdTabs[*].xsdHandlers`. Это ожидаемый результат согласованной публикации; runtime diff не следует использовать отдельно от исходных настроек и BPMN.
- `forms/*.json` меняют опубликованные XSD по проверенным ID: добавляют отдельные счётчики ожидающих, ранее отсутствовавших записей и технических ошибок; название столбца состояния; метку контрольной точки `(МСК)`. Идентификаторы исходных форм сохраняются.
- `handlers/*.js` содержат новые тела обработчиков под прежними GUID/name. Все запросы из этих обработчиков читают данные; массовые CREATE/UPDATE/DELETE, чтение ZIP/XLSX и локальные блокировки вкладок отсутствуют.

Формат diff содержит `collection`, `id`, JSON Pointer `path`, `expectedSha256` старого содержимого и новое `value`. `valueFile` указывает тот же текст в отдельном JS. Для XSD проверяется `expectedXsdContentSha256` — SHA-256 UTF-8 `JSON.stringify(xsdContent)` без пробелов. До применения требуется сверить текущую запись, каждый old hash и GUID/name; несовпадение означает новый source drift. В пакете нет HTTP-кода применения или выгрузок реальных дел.

Формы читают `rbuImportResult`, компактный `importDraft`, `rbuPetRollbackPlan` и `rbuPetRollbackReport`. Подтверждение импорта связывается с `confirmationFingerprint`; отката — с `targetAppealId` и `journalFingerprint` в `xsdData.rbuPetRollbackConfirmation`. ПГС сохраняет значения штатным действием формы, Java повторно проверяет их перед записью. Обновление страницы читает устойчивый прогресс сервера и не создаёт признак «другая вкладка».

`checkpointAt` остаётся ISO UTC в backend; форма показывает готовый `checkpointTimeDisplay` по Москве под меткой `(МСК)`. Состояния `PENDING`, `DELETED`, `ALREADY_DELETED`, `BLOCKED`, `ERROR` и причины берутся из backend отдельно. Неизвестное состояние останавливает отображение с явной ошибкой.

Для выбора исходного дела сохраняются проверенные привязки `47160 → 47012`, `47347 → 47346`, `47610 → 47615`. Короткий resolver задаёт номер стандарта из этой карты, без поиска единственного process key среди утверждённых копий. Backend ищет исходное дело по `mainId`, проверяет владельца и собственный журнал worker; старые Groovy-журналы не объявляются совместимыми автоматически.

## Локальная проверка

Из корня репозитория:

```cmd
node integration\pet\verify.mjs
```

Проверка разбирает manifest/diff, проверяет hashes артефактов, синтаксис обработчиков, отсутствие клиентских записей и выполняет сценарии чтения результата, различения состояний и отклонения устаревших подтверждений. При генерации XML отдельно разобран стандартным XML-парсером; сохранность исходных IDs, отсутствие тяжёлых скриптов и ссылки переходов сверены с частным текущим снимком.

Остаётся штатная проверка на целевом стенде: контекст регистрации, фактическое сохранение полей формы, возобновление задачи и переходы ПГС вплоть до штатного завершения. Локальные проверки этого не заменяют.
