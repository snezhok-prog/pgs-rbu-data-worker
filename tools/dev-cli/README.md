# Проверка external tasks из CMD

Клиент создаёт отдельный приёмочный процесс Camunda и собственную тестовую запись `rbuModulesAppeals`, загружает файлы в хранилище ПГС и запускает Java-worker на вашем ПК. Java забирает задачи со стенда исходящими запросами; подключение DEV к вашему ПК не требуется. Postman, PowerShell и Node.js для этих команд не нужны.

Этот процесс запускается напрямую через REST Camunda. Он не публикует стандарт ПГС, не имитирует регистрацию дела кнопками и не выставляет делу статус «Завершено». Приёмочный процесс и стандарт ПГС — разные объекты. DEV-откат из этого клиента не запускается; проверки отката выполняются локальными тестами.

## 1. Подготовить инструменты и контекст

Нужны JDK **25**, Maven **3.9.16**, доступ к разрешённым API DEV и распакованный SDK из артефакта Эволенты. Распаковывайте JAR из `BOOT-INF/lib` в отдельную папку; библиотеки в Git не добавляются. Совпадение SDK будет проверено по `docs/sdk-library-lock.json`.

Откройте обычный **CMD** в корне репозитория:

```cmd
set "JAVA_HOME=C:\Java\jdk-25"
set "PATH=%JAVA_HOME%\bin;C:\Maven\apache-maven-3.9.16\bin;%PATH%"
java -version
mvn -version
scripts\build.cmd
tools\dev-cli\dev.cmd build
```

Замените пути фактическими. Первая сборка выполняет JUnit и четыре набора проверок общей логики; вторая компилирует CMD-клиент и выполняет его отдельные локальные контрактные тесты. Контрактные тесты клиента используют синтетические данные и не обращаются к DEV.

Создайте локальный контекст, например:

```cmd
mkdir runtime\contexts
copy tools\dev-cli\context.example.json runtime\contexts\dev.local.json
notepad runtime\contexts\dev.local.json
```

В примере стоят недействительные значения. Их необходимо заменить данными **одного DEV-контура**:

| Поле | Откуда взять |
| --- | --- |
| `coreUrl` | Разрешённый внутренний API `sier-core-external` с окончанием `/int/api/v1/`; адрес из конфигурации/инструкции DEV. Это не адрес главной страницы ПГС. |
| `engineUrl` | Доступный REST Camunda с окончанием `/engine-rest/`. Нужны права на deployment, запуск процесса и собственные задачи. |
| `uiBaseUrl`, `uploadUrl` | Корень DEV ПГС и точный URL штатного запроса загрузки файла из Network браузера. Загрузка должна идти на тот же origin, что и интерфейс. |
| `cloudConfigUrl` | Разрешённый адрес конфигурации файлового сервиса DEV, возвращающий `propertySources`. Используется только адаптером файлов. |
| `storageEndpoint` | Ожидаемое значение `app.filestorage.s3.url` для того же DEV. Адаптер проверяет совпадение. |
| `standardCode` | Код для привязки испытательной подуслуги и allowlist worker. При наличии подготовленного стандарта DEV используйте его номер. В отдельном приёмочном процессе допустим согласованный код исходного стандарта: это не означает, что такой стандарт перенесён или опубликован на DEV. Клиент не читает каталог стандартов и не публикует их. |
| `organization._id`, `organization.name` | ID и название тестовой организации ПГС: ID находится в URL карточки организации в кабинете администратора. Это владелец тестовой записи. |
| `region._id` | ID действующего паспорта субъекта на DEV из URL его реестровой записи. |
| `municipality._id` | ID действующего паспорта МО этого субъекта из URL его реестровой записи. |
| `card._id` | ID действующей карточки организации в реестре оргмодуля, связанной с выбранными регионом, МО и организацией ПГС. Это отдельный ID, не `organization._id`. |
| `fileAdapterPort` | Свободный локальный порт, например `18085`. Одновременно используйте один адаптер на этом порту. |
| `allowHttp` | `true`, только если согласованные внутренние адреса DEV используют HTTP. Никакого отключения проверки TLS не выполняется. |
| `apiIntegrationVerified` | `true` после проверки указанных адресов и контракта API для этого контура. Иначе worker откажется изменять реестры. |

Все четыре ID — Mongo ObjectId из 24 шестнадцатеричных символов. Выбирайте записи, реально связанные между собой: формальное совпадение формата ID не подтверждает правильность организации или региона. Получать эти сведения можно через обычные карточки DEV и разрешённые запросы из Network; доступ к чужим данным не требуется. Секретов, Cookie, паролей и токенов в контексте быть не должно. Папка `runtime` исключена из Git.

## 2. Подготовить отдельный запуск и посмотреть BPMN

Пример для торговли, тип НТО:

```cmd
tools\dev-cli\dev.cmd init trade01 TRADE runtime\contexts\dev.local.json "НТО"
notepad runtime\dev-cli\trade01\acceptance.bpmn
```

Для других типов используйте новый запуск и `"Рынки"` или `"Ярмарки"`. Для рекламы:

```cmd
tools\dev-cli\dev.cmd init ads01 ADVERTISING runtime\contexts\dev.local.json
```

Имя запуска: 2–21 строчная латинская буква/цифра, первый символ — буква. Клиент добавляет случайный суффикс к process key и topic. Чужие задачи и общие топики не обслуживаются. `init` только создаёт локальные файлы; запросов на DEV ещё нет.

В дальнейшем вместо `trade01` подставляйте выбранное имя во **всех** командах. Существующий запуск повторно не инициализируйте: он хранит ID процесса, журнал и сведения о файлах.

## 3. Развернуть BPMN, создать собственную запись и загрузить файлы

После просмотра BPMN выполните:

```cmd
tools\dev-cli\dev.cmd deploy trade01
tools\dev-cli\dev.cmd create trade01 ROIV
tools\dev-cli\dev.cmd upload trade01 "C:\PGS\input\import.xlsx" --session
```

Для муниципального сценария укажите `OMSU` вместо `ROIV` при создании **нового** запуска. `create` создаёт только собственную тестовую запись в статусе `process`; это не штатная регистрация заявления ПГС.

**Авторизация загрузки на текущем DEV — через сессию браузера.** Войдите в DEV ПГС, в DevTools → Network выберите свой успешный запрос к этому ПГС и скопируйте значение заголовка **Cookie** из Request Headers. Вставьте его в скрытый запрос CMD и нажмите Enter: символы не отображаются. Секрет используется только в памяти текущей команды и не записывается в настройки, журнал или командную строку. Не отправляйте его в чат и не сохраняйте в файл. Одна загрузка не продлевает сессию браузера.

Не копируйте `Authorization: Bearer null`: на текущем DEV это не рабочий способ входа. Для другого контура, где подтверждена токенная авторизация, доступен явный `--token`; токен тоже вводится скрыто. Перенаправления авторизованной загрузки автоматически не выполняются.

Клиент отправляет XLSX в **настоящее хранилище ПГС** с `entryName=rbuModulesAppeals` и ID созданной им записи. Ответ проверяется, метаданные прикрепляются к записи, результат перечитывается. Размер каждого файла ограничен 20 МиБ.

Если Excel ссылается на документы или изображения, сначала загрузите их:

```cmd
tools\dev-cli\dev.cmd upload-documents trade01 "C:\PGS\input\documents" --session
```

Команда выбирает PDF/JPG/JPEG/PNG/DOCX непосредственно в указанной папке, максимум 64 файла; XLSX и подпапки пропускает. Cookie вводится один раз на пакет. Имя каждого файла должно совпадать со ссылкой в Excel. Уже загруженные файлы с тем же именем и SHA-256 повторно не отправляются. Один дополнительный файл можно передать через `upload-extra trade01 "C:\PGS\input\documents\photo.jpg" --session`. После загрузки дополнительных файлов сообщение сообщает, что группа документов будет привязана на этапе `Setup`: для неё сначала нужна подуслуга созданного процесса.

Все файлы должны быть загружены **до** команды `start`. Метаданные и SHA-256 сохраняются в `runtime\dev-cli\trade01\files.json`; этот список разрешает адаптеру читать только файлы своего запуска. Файл не раздаётся из локальной исходной папки: адаптер читает загруженный объект из S3 и сравнивает SHA-256.

## 4. Запустить адаптер файлов и Java-worker

Оставьте первое окно CMD для команд. Во **втором** окне CMD, с настроенным `JAVA_HOME` и из корня репозитория:

```cmd
tools\dev-cli\dev.cmd files trade01 "C:\SDK\BOOT-INF\lib"
```

Сначала проверяются все 258 SDK JAR по SHA-256, затем компилируется адаптер. Он слушает только `127.0.0.1`, загружает разрешённую конфигурацию файлового сервиса и держит реквизиты S3 только в памяти; в файлы и логи их не выводит. В консоли появятся ID/размер/SHA-256 прочитанных файлов. Произвольные объекты S3 и файлы других запусков не выдаются. Нужны штатные сетевые права к конфигурации и хранилищу DEV.

В **третьем** окне CMD:

```cmd
tools\dev-cli\dev.cmd worker trade01 --write
```

Это Java на вашем ПК. `--write` явно разрешает изменения только через проверенный обработчик и его контекст. Без него worker работает с запрещённой записью. В этом окне видны получение и выполнение external tasks. Не запускайте два worker для одного запуска; локальный журнал рассчитан на один процесс. Для остановки адаптера и worker — **Ctrl+C** в соответствующем окне. Папку журнала между перезапусками сохраняйте.

## 5. Выполнить импорт и сверить результат

Вернитесь в первое CMD:

```cmd
tools\dev-cli\dev.cmd start trade01
tools\dev-cli\dev.cmd status trade01
```

`start` запускает свой process key напрямую в Camunda, привязывает подуслугу к собственной записи и создаёт для неё группу «Файлы миграции» отдельным запросом к `rbuModulesAppeals/documents`. Сохранение группы и каждого файла проверяется повторным чтением. Корневое поле `documents` через общий PUT не изменяется: платформа может проигнорировать такую запись. Только после подтверждённой привязки файлов клиент завершает подготовительную задачу `Setup`. Дождитесь завершения `PARSE_VALIDATE` в консоли Java и появления задачи `Confirm` в `status`.

Откройте `runtime\dev-cli\trade01\status.json`: там сохранены полная собственная запись, результат валидации, текущие задачи и incidents. Если `isValid=false` или есть блокирующие ошибки, импорт не подтверждайте; исправьте исходный файл и создайте **новый** запуск. Клиент не обходит отрицательную валидацию.

После успешной проверки:

```cmd
tools\dev-cli\dev.cmd confirm trade01
tools\dev-cli\dev.cmd status trade01
```

Для торговли `confirm` перечитывает актуальные файл, тип данных, подуслугу и `confirmationFingerprint`. Устаревший отпечаток или изменённый файл не подтверждаются. Команда не подставляет произвольное значение.

После `IMPORT_APPLY` процесс ждёт на задаче `Inspect`. Сверьте записи в реестрах с Excel. ID записей и журнал импорта находятся в `status.json` → `appeal.subservices` и соответствующих полях результатов обработчика; открывать их можно через реестровые формы DEV. Обработчик также сохраняет ссылки на результаты там, где это предусмотрено отраслевым контрактом.

Для проверки повтора того же шага на **собственных** тестовых данных:

```cmd
tools\dev-cli\dev.cmd next trade01 --repeat
tools\dev-cli\dev.cmd status trade01
```

Дождитесь возврата на `Inspect` и убедитесь, что количество и ID записей не изменились. Для завершения приёмочного процесса:

```cmd
tools\dev-cli\dev.cmd next trade01
tools\dev-cli\dev.cmd status trade01
```

Ожидается `processState=COMPLETED`, пустые `tasks` и `incidents`. Статус самой записи ПГС остаётся `process`: клиент не подменяет проверку финального статуса стандартного дела. Передачу по кнопкам интерфейса и завершение через стандарт проверяют отдельно после восстановления публикации ПГС.

## Если команда прервалась

Каждая изменяющая операция сначала записывает `pending` в локальный `state.json`. Если ответ потерялся, нельзя считать, что сервер ничего не сделал: клиент блокирует слепой повтор. Сохраните папку запуска, выполните `status` и проверьте результат на сервере по ID/маркеру. Не удаляйте `pending`, записи или journal для получения зелёного результата. Встроенного автоматического восстановления неизвестного результата здесь нет; нужен разбор конкретной операции.

При явном HTTP 401/403 **текущей** запрещённой операции клиент разрешает повтор после восстановления доступа. Отказ чтения или посторонней команды не снимает старую неопределённость. При ошибках загрузки Cookie заново берётся из действующей собственной сессии.

## Граница проверки

Клиент поддерживает рекламу и торговлю; питомец сюда не включён. Локальный тест клиента проверяет формирование запросов и защиту от неверного владельца/отпечатка/повтора с синтетическим транспортом. Он не доказывает работу с конкретным DEV — это отдельный живой запуск с вашей конфигурацией. Самостоятельный runner собирается из публичных Maven-зависимостей; SDK файлового адаптера проверяется отдельно. Совпадение SDK не означает, что добавленные POI и JUnit входят в платформенный SDK.
